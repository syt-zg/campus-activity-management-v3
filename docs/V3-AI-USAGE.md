# AI 工具使用与工程过程说明

> 对应实验要求「五、AI 工具与工程过程」。
> 本文不提交 AI 对话原文，只说明三件事：**为什么调整、调整了什么、如何确认调整有意义**，
> 以及关键结果是**怎么被核查**的。

## 一、AI 在哪些环节被使用

| 环节 | 用法 | 是否直接采纳 |
|---|---|---|
| 数据发现 | 编写 `analysis/analyze.py` 做描述性统计、生成报告骨架 | 数字全部自行复核（复跑脚本、抽查原始 CSV） |
| 需求判断 | 提出需求候选、给出取舍矩阵 | 部分采纳，部分被数据推翻（见第四节） |
| 实现 | 编写后端接口、前端页面、测试脚本 | 逐文件跑语法检查与测试后才保留 |
| 测试 | 生成三组测试脚本（冒烟/渲染/性能对比） | 断言由本组定义，脚本可复跑 |
| 文档 | 整理变更清单与验证记录 | 结论与数字以测试输出为准 |

**没有直接采纳的部分**：AI 生成的界面文案、指标口径、优先级排序，均经过本组按数据与管理口径重写或调整。

## 二、为什么调整（三个理由，均有数据或代码依据）

### 理由 1：V2.0 只存结果不存过程

全量检索 V2.0 源码，`签到 / 出席 / 通知 / 统计 / 趋势 / 反馈 / 日志 / 埋点 / 取消原因`
命中数全部为 0。报名之后是否到场、为什么退出、名额是否被占住，系统都答不出来，
所以每轮「基于运行数据演化」都只能靠外部数据包喂。
→ 这是本轮最主要的需求来源，不是"想加个日志功能"。

### 理由 2：有一条承诺了却没落地的规则

`eligibility`（报名资格）在发布活动时被保存、列表里也展示，
但报名接口 `POST /api/activity/:id/join` 从未读过这个字段。
也就是说"限制资格"是假的，任何学生都能报名。
→ 属于**实现与承诺不一致的缺陷**，改动小、证据硬。

### 理由 3：模拟数据直接指向两处问题

| 数据事实 | 指向的改动 |
|---|---|
| 24 个活动的报名开放时刻只有 09:00 / 18:00 两档，42.8% 的报名发生在开放当小时；09:00 时段 P50 从 210ms 抬到 850ms，42.4% 请求超 1 秒 | 活动可配置报名开放时间（错峰）+ 写入合并 |
| 126 条 `duplicate` 记录 100% 对应 `client_retry=1` | 报名请求幂等（`requestId`） |
| 热门活动候补人数达名额的 3～5 倍，整体候补转化率仅 14.8% | 候补深度提示 + 管理员候补压力表 |

## 三、调整了什么（摘要，完整清单见 `docs/V3-CHANGES.md`）

| 类型 | 内容 |
|---|---|
| 新增功能 | 运行事件日志、运行统计/运行日志页、资格校验、递补确认窗口与超时释放、取消原因、出席记录、名单导出、错峰开放、请求幂等、候补深度提示 |
| 修复缺陷 | 资格字段不生效；删除活动丢失历史（改归档）；申请时间早 8 小时（UTC/本地混用）；版本号三处不一致 |
| 性能改动 | 写入合并（50ms 窗口）+ 备份降频 60 秒 |
| 明确不做 | 推送通知、移动端适配、SQLite 迁移、统计大屏、列表分页（理由见变更文档「实施边界」） |

## 四、AI 的判断被数据推翻的一处（关键核查案例）

**AI 最初的判断**：候补转化率只有 14.8%，说明"递补机制没有闭环"，应该加强自动化递补。

**数据核查后的事实**：取消报名 130 条、候补转正式 130 条，两者相等 ——
**每一次名额释放都成功递补了**，机制本身没有漏。
真实原因是候补池深度达到可释放名额的 6.7 倍（例如某活动 31 个名额、146 人候补）。

**处理方式**：撤销"加强递补自动化"的方案，改为解决**等待预期**（候补深度提示）
与**需求集中**（错峰开放）。这条修正完整记录在 `analysis/REPORT-数据发现.md` 第二节。

保留这个案例的原因是：它说明关键结论确实经过了核查，而不是把 AI 输出直接当成结论。

## 五、如何确认调整有意义（不靠"演示一遍没报错"）

### 5.1 三组可复跑的测试

| 测试 | 覆盖 | 结果 |
|---|---|---|
| `tests/v3-smoke.js` | 37 项：登录、资格拦截、错峰开放、幂等去重、候补位次、取消原因、自动递补、确认超时释放与顺延、出席、导出、归档、统计、日志筛选、回归 | 37/37 通过 |
| `tests/ui-render.js` | 20 项：三种角色共 11 个视图在 jsdom 中真实执行脚本，任一视图抛异常即失败 | 20/20 通过 |
| `tests/perf-compare.js` | 同负载（60 并发报名）、同机器、3 轮平均的前后对比 | 总耗时 628ms → 223ms（-64%），落盘 61 次 → 2 次 |

实际输出原样保存在 `docs/V3-VERIFY.md`，未验证项也列在其中。

### 5.2 验收标准是先写好的，不是事后凑的

每条需求在实现前就定了"通过线"，例如：

- 资格校验：造 3 组用例（错学院、错年级、正常），必须 3/3 判定正确；
- 超时释放：把确认窗口通过 `WAITLIST_CONFIRM_HOURS` 压到 4 秒跑 5 组，必须 5/5 释放并顺延；
- 幂等：同一 `requestId` 提交两次，正式参加人数必须仍为 1；
- 回归：三角色各一条主路径 + 候补递补路径，必须全部通过。

### 5.3 承认的局限

- 60 并发只是机制验证，不等于生产容量；
- 打包版只验证了服务层（`/api/health` 返回 V3.0、管理员可登录），界面流程需手工过一遍；
- 模拟数据来自教师构造的另一套平台，**不能当作本系统实测结果**，
  本系统的性能结论只以 `perf-compare.js` 为准。
