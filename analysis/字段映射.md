# 数据包字段 ↔ 本系统字段对照表

> 用途：证明"数据发现"能落到本组系统上，而不是拿别人的系统讲故事。
> 结论先说：**6 张表里 4 张能对上，2 张对不上**；对不上的地方就是需要新增的能力。

## 一、能对上的部分

| 数据包 | 字段 | 本系统对应 | 对应关系说明 |
|---|---|---|---|
| activity.csv | `activity_id` | `activities[].id` | 数据包是字符串编号，本系统是自增数字，只能按行序/名称映射，不做一对一假定 |
| activity.csv | `category` | `activities[].type` | 取值域不同（数据包 10 类，系统 7 类），统计需先归并 |
| activity.csv | `organizer_id` | `activities[].publisherId` | 教师账号 |
| activity.csv | `activity_start` | `activities[].startTime` | 直接对应 |
| activity.csv | `capacity` | `activities[].maxParticipants` | 直接对应 |
| activity.csv | `location` | `activities[].location` | 直接对应 |
| activity.csv | `registration_open` | **V3.0 新增** `registrationOpen` | V2.0 没有这个字段（发布即可报名）；本轮补齐 |
| registration_log.csv | `action=apply` | `POST /api/activity/:id/join` | 一次申请一次请求 |
| registration_log.csv | `action=cancel` | `DELETE /api/activity/:id/join` | V3.0 起带 `reason/note` |
| registration_log.csv | `result=accepted` | `registrations[].status=正式参加` | 对应 |
| registration_log.csv | `result=waitlisted` | `registrations[].status=候补中` | 对应 |
| registration_log.csv | `result=duplicate` | **V3.0 新增** `join_duplicate` 事件 | 本轮用 `requestId` 去重并留痕 |
| registration_log.csv | `result=capacity_conflict` | 无对应（单进程串行，不产生该结果） | **差异**：本系统不会出现该结果，故不新增 |
| registration_log.csv | `result=server_error` | HTTP 500 + 异常日志 | 有，但未细分 |
| registration_log.csv | `latency_ms` | 内存耗时采样 `perf` + `slow_request` 事件 | V3.0 起可对比 |
| registration_log.csv | `client_retry` | `requestId` 幂等键 | 语义不同：数据包是客户端自报，本系统是服务端去重 |
| waitlist_log.csv | `new_status=waiting` | `status=候补中` + `waitlistTime` | 对应 |
| waitlist_log.csv | `new_status=accepted` | `status=正式参加` + `confirmDeadline` | V3.0 增加确认窗口 |
| waitlist_log.csv | `reason_code=CAPACITY_FULL` | join 满员分支 | 对应 |
| waitlist_log.csv | `reason_code=SLOT_RELEASED` | `promoteFromWaitlist()` | 对应 |
| system_log.csv | `level` / `component` / `event_code` | `events.jsonl` 的 `type` / `result` | 粒度更粗，字段名不同，可语义映射 |
| system_log.csv | `elapsed_ms` | 事件 `durationMs` | 对应 |

## 二、对不上的部分（= 能力缺口）

| 数据包 | 字段 | 本系统现状 | 处理方式 |
|---|---|---|---|
| user_behavior.csv | `page` / `event_name` / `session_id` / `device` | **没有前端埋点**，只有服务端业务事件 | 记为缺口：本轮不做。原因：桌面单机应用的价值低于成本，且模拟数据不能证明本系统需要 |
| feedback.csv | `feedback_text` | **没有反馈收集入口** | 记为缺口：本轮不做。V3.0 的取消原因只覆盖"退出"这一个场景，不覆盖整体评价 |
| registration_log.csv | `result=capacity_conflict` | 无对应分支 | 不新增，理由见上 |

## 三、映射时踩到的三个坑（写进报告）

1. **粒度不一致**：`user_behavior` 是埋点级，`registration_log` 是请求级，`waitlist_log` 是状态变化级。
   把三者的"次数"相加会重复计数，任何比率都要先声明用的是哪张表。
2. **`activity_id` 不能假定一对一**：数据包 24 个活动、本系统 21 个活动，编号体系不同；
   只能按"名称 + 类型 + 容量"做近似匹配，报告中不做活动级的精确对照。
3. **取消原因无字段**：数据包只有 `reason_code`（CAPACITY_FULL / SLOT_RELEASED），
   那是**候补变化原因**，不是**学生取消原因**。因此 V3.0 的取消原因枚举来自 V2.0 访谈整理，
   属于**假设**，本轮数据无法验证——报告中已明确标注。

## 四、由对照直接产生的 5 处代码改动

| # | 数据证据 | 改动 |
|---|---|---|
| 1 | 24 个活动只有 09:00/18:00 两个开放时刻，42.8% 报名发生在开放当小时 | 新增 `registrationOpen`，未到时间禁止报名，前端按钮直接显示开放时间 |
| 2 | 126 条 `duplicate`，100% 对应 `client_retry=1` | 报名接口加 `requestId` 幂等，重复提交返回首次结果并记 `join_duplicate` |
| 3 | 09:00 时段 P50 从 210ms 升至 850ms，42.4% 慢请求 | 写入合并（50ms 窗口）+ 备份降频；本机 60 并发对比：631ms → 225ms |
| 4 | 候补转化率 14.8%，热门活动候补达名额 3～5 倍 | 报名响应返回候补深度；卡片显示"候补是名额的 N 倍"提示；管理员新增候补压力表 |
| 5 | 全量请求需要 P50/P95 才有意义（只记慢请求会有采样偏差） | 增加内存耗时环形采样，统计页展示接口 P95 与慢请求占比 |
